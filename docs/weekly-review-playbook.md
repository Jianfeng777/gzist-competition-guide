# 每周赛事数据审查与发布规范

本规范供自动任务和维护人员使用，不在学生端展示。目标是在不误导学生的前提下，每周复核赛事官网、报名入口、报名月份和比赛简介，并把可确定的变化直接发布到 GitHub Pages。

## 一、信息来源优先级

1. 学校最新正式竞赛目录决定赛事是否收录、等级、序号、名称和主办方。没有新目录时，不因当届消息缺失而删除项目。
2. 赛事主办方官网、赛事官方专题页、官方报名系统和主办方正式通知用于确认届次、报名状态、月份和入口。
3. 政府部门、主办单位或官方组委会发布的通知可作为补充证据。
4. 其他学校的通知、喜报、搜索结果、百科、聚合站和培训机构页面不得作为学生端官网或报名入口。它们最多只能提供检索线索，最终结论仍须回到官方来源。
5. 官网入口必须指向赛事主页或官方专题页；报名入口必须是当前届次仍开放的官方入口。两者分开维护。

## 二、每周审查队列

每周任务先生成审查队列。默认目标为约 50 项；必须复核项可以突破上限。全部已登记链接另做 HTTP 健康检查，不占用深度语义审查名额。

- P0 结构异常：学校发布新目录、赛事更名或合并、等级或序号变化、主办方改变、同一父项出现无法可靠合并的新赛项。此类项目暂停自动结构修改并提醒维护者。
- P1 当前可报名：`registration.state=open` 的赛事每周复核，确认入口仍可用、截止日期未过、当前届次一致。
- P1 当前或下月：报名月份包含当前月或下一个自然月的赛事优先复核；除当前开放项目外，14 天内已经深度复核过的可暂缓一次，把名额留给待确认项目。
- P2 入口风险：官网或报名入口出现 404/410、跳转到无关页面、证书异常、登录/验证码阻断，或入口长期未核验。
- P2 待确认轮换：月份待确认、暂无官网或官网未核验的项目按“最久未审查优先”轮换，确保所有待确认项目持续被重新检查。
- P3 常规复核：其余项目按最近审查日期轮换；稳定项目最长不应连续 8 周不检查。

审查状态写入 `data/review-state.json`。生成队列时，数据状态、临近月份和上次审查时间共同决定优先级，不能只检查已经有链接的项目。

## 三、逐项审查方法

每个项目至少执行以下步骤：

1. 搜索赛事完整名称、主办方和当前或下一届年份。
2. 优先打开官方赛事主页，再查看官方通知、章程和报名系统。
3. 核对页面主体、域名、主办单位、届次和报名日期，避免把同名赛事或子赛项误合并。
4. 需要浏览器确认时逐个打开链接，只读取少量指定元素并截取当前视口；禁止整页截图、整页 DOM、正文全文或大批量 CDP 数据，避免 `native pipe message exceeds frame limit`。
5. 记录本次检查日期、结果、核对字段、证据链接、简短说明和下次建议检查日期。

## 四、自动更新与异常升级

以下情况可直接更新并发布：

- 官方页面明确发布新一届通知、报名开始或截止时间。
- 官方报名入口明确开放、关闭或更换。
- 官网明确迁移到新的官方域名或专题页。
- 报名月份能够从官方日期确定；区间必须写入其中每个月，例如 3—5 月保存为 `[3, 4, 5]`。
- 赛事简介能够从官方章程或可信资料提炼为学生实际要完成的任务。
- 本周没有新消息，但已完成复核；更新审查状态，赛事继续保留，未核实入口继续关闭。

以下情况不得自行猜测，需要创建或更新 GitHub Issue 并提醒维护者：

- 学校发布了新版目录，或收录范围、等级、序号发生结构变化。
- 官方来源互相冲突，无法判断哪个日期、届次或入口有效。
- 官网需要账号、短信、验证码、校园权限或其他无法自动完成的访问条件。
- 官方页面已消失且找不到可确认的新官网，或只能找到其他学校喜报、转载和搜索摘要。
- 同一学校目录父项下出现多个子赛项，无法可靠确定应展示哪个官网或报名入口。
- 需要删除赛事、合并 ID 或批量改名等可能破坏历史链接的操作。

遇到异常时，学生端采用保守状态：赛事继续保留；官网显示“暂时无官网”或保持已核实的稳定主页；报名按钮关闭；说明写清“待确认”或建议查看官方通知。

## 五、数据写入规则

- `data/school-catalog.json`：只有学校正式目录更新时才修改。
- `data/open-registration.json`：写入明确核实的当届报名状态、官方入口、月份、证据和 `checkedAt`。
- `data/registration-timing.json`：保存月份及其来源类型。学生清单只显示月份或“待确认”，但数据层继续保留 `verified_2026`、`historical`、`unknown` 等来源信息。
- `data/verified-details.json`：补充官网、比赛内容、准备建议和证据；不得用其他学校喜报替代官网。
- `data/review-state.json`：保存每次审查记录和下次复核日期。
- `data/catalog.json`、`site/data.js`：由构建脚本生成，不手工编辑。

## 六、构建、校验与发布

每次审查开始前同步 `origin/main`，结束后依次运行：

```bash
node scripts/build-catalog.mjs
node scripts/validate-catalog.mjs
node scripts/validate-summaries.mjs
node scripts/validate-review-state.mjs
node scripts/build-review-queue.mjs --limit 50 --markdown review-queue.md --json review-queue.json
node scripts/check-links.mjs --report link-audit.md
```

校验通过后再提交源数据、审查状态和生成结果。正常变更可直接更新 `main`，由 Pages 工作流发布。发布后用线上页面验证：总数仍为 204（除非学校新版目录已人工确认）、筛选可用、当前报名入口状态正确、控制台无错误。

每周任务最终应给出：审查数量、自动更新数量、确认无变化数量、仍待确认数量、失效入口数量、需要人工处理的异常，以及对应 GitHub 提交或 Issue 链接。
